# 再現可能な生バイト mutation の基盤を実装する

Status: open
Model: GPT-6 Astra Pro
Created: 2026-10-29
Updated: 2026-10-29
Branch: feat/20261029-byte-mutators

## 概要

seed と設定を固定すると同じ候補列を生成できる Rust の byte mutator を追加する。対象の実行や coverage の判断から独立した候補生成 API とし、入力長と生成件数の上限を守る。

## 背景

- [README の次期計画](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/README.md#L83-L97) は mutation loop を未実装としている。
- [現在の CLI](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/poc/cli.mjs#L15-L20) は指定された入力を一回実行し、新しい入力は生成しない。
- [MoonBit acceptance test](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/test/moonbit.test.mjs#L35-L43) は生バイトの固定ケースを使用しており、mutation の探索能力や再現性を検証するものではない。

## 問題

入力を変異させる処理、乱数列の再現契約、候補長・生成件数の制限がない。乱数ライブラリの既定実装や実行時間を暗黙の seed に使うと、失敗を発見した探索条件を再利用しても同じ候補列を得られない。

## 目標

- 同じ version・初期 seed・設定・同じ順序の基底入力から、同じ候補列を得る。
- 小さな byte 操作で新しい候補を作り、基底入力を変更しない。
- 候補生成を有限にし、後続の campaign が実行予算と組み合わせられるようにする。

## 対象外

- target の起動、campaign loop、corpus の選択・保存、coverage による採用判断。
- structured generator、辞書・文法ベースの mutation、複数入力の crossover。
- failure shrinking、失敗署名、再現確認、CLI コマンドの追加。
- 並列 worker 間の乱数分配、実行時間に基づく停止、探索効率の最適化。

## 提案する方針

1. Rust workspace に候補生成専用の `mutator` モジュールを置く。呼び出し元が基底入力を渡し、generator は候補または生成終了を返す。corpus を自分で選ばず、supervisor を呼び出さない。
2. 固定幅の seed と明示した乱数アルゴリズムを使用する。乱数から操作・位置・値を選ぶ方法と操作の順序も含めて version を付け、依存ライブラリ更新だけで候補列が変わらないようにする。
3. 最初の操作を一 bit の反転、一 byte の置換、一 byte の挿入、一 byte の削除に限定する。一候補につき一操作とし、入力の内容を文字列として解釈しない。
4. 空入力では挿入、上限長では挿入以外など、適用可能な操作から選ぶ。位置の範囲と整数演算を検証し、不可能な操作を再抽選し続けない。
5. 最大入力長と最大候補数を設定で受け取る。長さ上限を超える基底入力はエラーにし、候補生成前に件数予算を確認する。最大候補数は target の実行件数を意味しない。
6. 適用できる操作がない場合は候補なしで終了する。例えば空入力かつ最大入力長ゼロは終了となり、無限ループや上限違反を起こさない。
7. version・seed・設定を呼び出し元が記録できる形で公開する。候補列を変える変更では version を更新し、再現の互換性範囲を記録する。

## 受け入れ条件

- [ ] 同じ version・seed・設定・基底入力列から生成される候補列が、再起動してもバイト単位で一致する。
- [ ] bit 反転、byte 置換・挿入・削除を個別に検証でき、元の入力バッファを変更しない。
- [ ] 空入力、最大長、最大長ゼロ、候補数ゼロ、上限超過した基底入力を明示した契約で処理する。
- [ ] 生成した候補は最大入力長を超えず、返す候補数は指定した予算を超えない。
- [ ] 適用可能な操作がない場合に有限時間で終了し、範囲外アクセスや整数オーバーフローを起こさない。
- [ ] 候補生成だけで subprocess、corpus、finding、coverage への副作用が発生しない。

## テスト計画

以下は実装時に追加・実行する計画であり、この Issue 作成時点では未実行。

1. Rust workspace 導入後に `cargo test --workspace` を実行する。
2. 固定 seed と複数の基底入力について候補列の期待値を保存し、version 内の再現互換性を検証する。対応する Ubuntu・macOS の CI でも同じ期待値を使う。
3. 操作ごとに空・一 byte・最大長の入力を与え、変更内容と基底入力の不変性を検証する。
4. 多数の固定 seed で長さと候補数の上限、適用不能時の終了を確認する。乱数統計や crash 発見率を PASS 条件にはしない。
5. 同じ seed でも基底入力の供給順が違えば同じ候補列を保証しないことを、API の再現条件としてレビューする。

## リスク

- RNG の seed だけでなく、操作選択や範囲への変換を変えても候補列が変わるため、version の対象範囲を限定しすぎない。
- 小さな byte 操作だけでは複雑な条件を発見しにくい。探索能力の拡張はこの基盤の再現契約を保った後続作業とする。
- 候補件数と実行件数を混同すると campaign の予算が破綻する。生成件数の契約を API に明記する。
- 基底入力列の供給順は呼び出し元の責任であり、並列 scheduling をこの Issue の再現保証に含めない。
