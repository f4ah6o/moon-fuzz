# 生バイトのコーパス保存と再読み込みを実装する

Updated: 2026-10-29

## 概要

入力ファイルを生バイトのまま取り込み、内容ハッシュで重複を除いて保存・再読み込みできる Rust のコーパス基盤を追加する。探索結果の採否を判断する前段として、保存された入力の同一性と完全性を保証する。

## 背景

- [README の次期計画と未実装一覧](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/README.md#L83-L97) は corpus management と mutation loop を未実装としている。
- [現在の CLI](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/poc/cli.mjs#L15-L24) は一つの入力を読み、finding の場合だけ保存する。
- [既存の finding 保存](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/poc/runner.mjs#L59-L75) は生バイトを保存するが、ハッシュと UUID の組で別々の証跡を作る機能である。

## 問題

複数の seed を取り込み、重複のない入力集合として保存し、別セッションで同じ入力集合を復元する API がない。finding の保存先を探索用コーパスとして流用すると、失敗の診断記録と探索入力の管理責務が混在する。

## 目標

- 空入力を含む任意のバイト列を損失なく import・保存・再読み込みする。
- 同じ内容は一件として扱い、破損や未完了の書き込みを完全な入力として返さない。
- coverage の有無に依存しない保存 API を、後続の探索ループから呼べるようにする。

## 対象外

- coverage による入力採用、corpus eviction、入力の選択順を決める scheduler。
- mutation、campaign loop、finding の重複排除・署名・縮小。
- CLI コマンドの追加、再帰的なディレクトリ取り込み、複数 writer の同時更新。
- 既存 finding の保存形式変更と、電源断に対する永続化保証。

## 提案する方針

1. Rust workspace に `corpus` モジュールを設け、保存先を開く、通常ファイルを import する、入力一覧と内容を読む操作を分ける。保存先は呼び出し元が指定し、finding の保存先から独立させる。
2. 入力の SHA-256 を識別子とし、例えば `inputs/<sha256>` に元のバイト列をそのまま格納する。UTF-8 変換や JSON 化を入力保存の経路に含めない。
3. 同じ識別子が存在した場合は内容の完全性と一致を確認して既存項目を返す。既存ファイルが破損している場合は上書きで隠さず、対象を特定できるエラーを返す。
4. 同じファイルシステム上の予約された一時領域に完全な内容を書き、書き込み完了後に rename して公開する。失敗時に既存入力を変更せず、一時ファイルは一覧へ含めない。
5. 再読み込み時は正規の名前、通常ファイルであること、実データのハッシュを検証する。入力一覧は識別子順で返し、filesystem の列挙順に依存させない。
6. 最大入力長を設定として受け取り、取り込み・読み込みで同じ上限を適用する。上限超過、読めないファイル、不正な項目を空コーパスや正常入力として扱わない。
7. 最初は単一 writer の契約に限定する。並行更新や coverage metadata は API を利用する後続 Issue で追加の必要性を判断する。

## 受け入れ条件

- [ ] 空、NUL、非 UTF-8、`00 ff` を含む入力が import と再読み込みでバイト単位に一致する。
- [ ] 別の名前で同じ入力を取り込んでも、保存項目と返される識別子は一つになる。
- [ ] 保存先を開き直すと同じ入力集合が識別子順に得られる。
- [ ] ハッシュ不一致、不正な項目、上限超過は対象を識別できるエラーになり、正常な入力として返らない。
- [ ] 書き込み途中の失敗で既存項目を変更せず、不完全な入力を公開しない。一時ファイルが残っても一覧から除外される。
- [ ] corpus 操作で finding の入力・metadata・ログを作成または変更しない。

## テスト計画

以下は実装時に追加・実行する計画であり、この Issue 作成時点では未実行。

1. Rust workspace 導入後に `cargo test --workspace` を実行する。
2. 一時ディレクトリで空入力、二進入力、重複、保存先再開、最大長ちょうど・超過を検証する。
3. 保存後の内容改変、不正な項目、一時ファイル残存、書き込み失敗を用意し、完全性検証と公開の原子性を確認する。
4. import 順と filesystem の作成順を変えても、読み戻す識別子順とバイト列が一致することを確認する。

## リスク

- rename による不完全ファイルの非公開と、電源断後の耐久性は別の保証である。最初の契約を前者に限定する。
- ハッシュ名だけを信用すると保存後の破損を見逃すため、読み込み時の検証を省略しない。
- 大きな入力の読み込みでメモリ使用量が増えるため、上限を読み込み処理にも適用する。
- 後続の scheduler が保存順を探索順と誤認しないよう、識別子順は再現可能な列挙の契約として記録する。
