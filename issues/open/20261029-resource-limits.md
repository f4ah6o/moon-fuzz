# Linux と macOS の CPU・メモリ制限の保証範囲を調べる

Status: open
Model: GPT-6 Astra Pro
Created: 2026-10-29
Updated: 2026-10-29
Branch: research/20261029-resource-limits

## 概要

Linux と macOS でターゲットの CPU・メモリ使用量を制限する候補を調査し、制限の単位、保証範囲、必要権限、未対応時の挙動を明らかにする。小さい実験と一次資料で成立条件を確認してから、通常の実装 Issue を作成する。

## 背景

- 基準コミットは `d9980543109290da8869789f860ac5a9d1c9af95`。
- [README](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/README.md#L40-L44) は、現在の停止対象が直接の worker であり、security sandbox ではないと説明している。
- [runner](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/poc/runner.mjs#L18-L33) は startup/execution の期限とログ上限を持つ。
- [未実装範囲](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/README.md#L94-L97) に resource limits があり、[CI](https://github.com/f4ah6o/moon-fuzz/blob/d9980543109290da8869789f860ac5a9d1c9af95/.github/workflows/ci.yml#L9-L24) は Ubuntu と macOS を対象にしている。

## 問題

経過時間の期限とログ上限だけでは、CPU・メモリ制限として何を保証するか定義できない。プロセス単位、子孫を含む集合、JS heap、native allocation などを区別した制限契約がない。

両 OS で同じ保証を提供できるかは未確認である。worker の終了 code/signal だけでメモリ上限超過を断定してよいかも調査が必要である。

## 目標

- CPU とメモリの計量対象、適用範囲、保証の強さ、必要権限を OS 別に説明できる。
- 利用できない環境で制限指定を無視せず、実行前に検出・報告する契約を提案する。
- 実験で確認できた機能だけを後続実装の受け入れ条件にする。

## 対象外

- 製品用 supervisor と resource limit 機構の実装。
- process-tree 終了処理そのものの実装、Windows 対応。
- 任意の悪意あるターゲットを実行する security sandbox。
- ホストの全メモリを消費する実験、管理設定や利用者全体の上限の変更。

## 提案する方針

1. 「CPU 時間」「経過時間」「メモリ」の候補定義を分ける。メモリについては heap、resident、virtual、子孫を含む集計のどれを保証するかを明記する。
2. OS と runtime の一次資料から候補を調べ、プロセス生成時の適用、継承、権限、利用可能な環境、超過時の通知・停止動作を比較する。
3. V8 heap 上限、native allocation、子孫プロセスの計測範囲を区別する。heap 上限だけを全プロセスのメモリ保証として表示しない方針にする。
4. Linux/macOS の各候補で小さい実験を行う。単一 worker と少数の子孫を分け、制限がどの単位に効いたかを観測する。
5. 実験を始める前に、十分小さい資源予算、短い外側の watchdog、最大子孫数、終了確認を設定する。上限の強制手段を確認できない環境では allocation 実験を実行しない。
6. 明示された上限を設定できないときは、実行前の infrastructure/usage error とする案を評価する。未対応の制限を黙って無効化する案は採用しない。
7. OS が確認できる超過理由と、単なる異常終了を区別する。確証のない終了を OOM や CPU 上限超過と断定せず、観測値と不明点を保存する契約を提案する。
8. OS 別の能力表、実行ログ、推奨案、未対応範囲を調査報告へ記録する。保証単位とエラー契約を確定できた範囲だけ、通常の実装 Issue にする。

## 受け入れ条件

- [ ] CPU・メモリの定義、適用対象、必要権限、対応 OS/環境、超過時の動作をまとめた能力表がある。
- [ ] 推奨案に一次資料と小さい実験の根拠があり、未実行・非対応の組み合わせを区別している。
- [ ] JS heap のみの上限と native allocation・子孫を含む制限を同一の保証として扱っていない。
- [ ] 未対応の上限を要求した場合のエラーと、実行前に検出できない制約を説明している。
- [ ] 超過原因が確認できる場合と、不明な異常終了の場合の分類・保存方針がある。
- [ ] 後続実装の範囲、process-tree 終了処理との境界、OS 別の検証条件を確定しているか、残る問いが明確である。

## テスト計画

1. OS/runtime の版、権限、選んだ上限と計量対象を記録し、公式仕様に照らして実験の前提を確認する。
2. CPU 実験は短い busy loop と待機する fixture を分け、CPU 使用量と経過時間を混同していないか確認する。
3. メモリ実験は低い上限と段階的な小さい割り当てで行い、heap、native、少数の子孫について観測範囲を分ける。ホストを枯渇させない。
4. 上限未対応、権限不足、設定失敗を再現し、ターゲットを起動せずに報告できるか検証する。
5. 超過時にも外側の watchdog が実験を終了させ、関連プロセスが残らないことを確認する。原入力と診断を保存する後続契約をレビューする。
6. `npm test` と `npm run test:moonbit` を既存挙動の基準として実行し、既存 timeout と新しい資源制限の分類が混同されていないか確認する。

この Issue 作成時には資源制限の実験・上記試験を実施していない。実行した組み合わせだけを PASS / FAIL とし、その他は未実行または未対応として報告する。

## リスク

- OS や実行権限によって保証が異なるため、両 OS で同じ制限を実現できると先に約束しない。
- 観測型の監視だけで厳密な上限を保証したと扱わず、検出遅延や超過分を能力表に残す。
- 不明な SIGKILL を資源制限超過と決めつけると、異なる crash を誤分類する可能性がある。
